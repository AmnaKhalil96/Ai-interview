# Reflection

## What was hardest, and why

The hardest part wasn't building any single feature — question generation, evaluation, auth, and Firestore all came together in a pretty straightforward way once I settled on the pattern of isolating each provider's SDK details into one file (`lib/ai/generateQuestions.ts`, `lib/ai/evaluateAnswer.ts`, `lib/firebase.ts`). The hardest part was diagnosing why the History page scored only 71 on mobile Lighthouse Performance when Landing scored 88, because the real cause turned out to be two layers deeper than it looked.

My first instinct was "it's the auth-then-fetch waterfall, obviously — that's just slow." That's partly true, but reading the actual Lighthouse JSON instead of trusting my assumption showed something more specific: LCP was the entire problem (a 0.10 score, ~6.3s), and the *element* Lighthouse was measuring against wasn't the loading spinner I'd already built — it was the empty-state paragraph that only appears once Firestore resolves. I hadn't understood that the browser's LCP algorithm keeps re-anchoring to whatever's the *largest* painted element so far, so my smaller "Loading…" text was getting quietly superseded by a bigger block of text that happened to render six seconds later. The fix wasn't "make it faster," it was "make the loading state visually as big as the thing that replaces it" — a completely different kind of fix than I expected to be writing.

Then, while checking whether Firebase's SDK itself was adding overhead, I found a second, unrelated problem hiding in the same score: Firebase Auth was proactively opening a hidden Google API iframe on every mobile page load, including pages that never touch Google Sign-In. Tracking that down meant reading into `@firebase/auth`'s own compiled source to find `_shouldInitProactively`, which turned out to just check `_isMobileBrowser() || _isSafari()` — a default I never would have found from documentation alone. That was the hardest kind of debugging in this whole project: not because the fix was complicated (it was two files, a handful of lines), but because getting to the real cause meant refusing to stop at the first plausible explanation twice in a row.

## What I'd do differently next time

I'd do the responsive and accessibility passes much earlier — ideally alongside each feature as I built it, not as a dedicated sweep near the end. When I finally sat down and tested every page at 375px and ran axe-core against every UI state, I found a real, recurring bug class I hadn't noticed at any point while building: flex items have a default `min-width: auto`, which means a bare text node inside a flex row sizes to its longest unbreakable "word" instead of respecting `max-width` — so a long AI-generated sentence, a pasted URL, or someone's typed answer could silently push a card wider than the screen, no matter how many `break-words` classes I'd already added elsewhere. That single CSS default caused the same-looking bug in at least three unrelated components (the feedback strengths/gaps list, the session summary breakdown, the answer textarea's mic button row), and I fixed each one the moment I found it rather than recognizing it as one root cause the first time. If I'd been testing at mobile widths from the start, I'd have caught the pattern once and applied `min-w-0` as a habit, instead of hunting the same bug down three separate times months apart.

## A genuine surprise

The flexbox thing above was the surprise, really — not that CSS has edge cases, but how *invisible* this one was. Every one of those components looked completely correct in isolation, rendered fine with realistic test data, and passed a casual glance on desktop. The bug only existed in the gap between "text that's usually short" and "text that's occasionally very long with no spaces in it," which is exactly the kind of input an AI model or a stressed-out interview candidate typing fast will eventually produce and a developer testing by hand won't think to. It changed how I think about testing UI that displays AI-generated or user-typed content: the realistic test case isn't the tidy one I'd type myself, it's the ugly edge case the model or the user will actually send.
